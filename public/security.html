Security Policy

Vulnerability disclosure, known limitations, and security architecture

Updated: March 2026 github.com/ishaanman7898/ShareSecure
Responsible Disclosure If you discover a security vulnerability, please report it privately — not as a public GitHub issue. Email ishaanmanoor1@gmail.com with details. We take all reports seriously and will respond promptly.

1. Reporting a Vulnerability

Please include the following in your report:

  • Description of the vulnerability and affected component
  • Steps to reproduce (if applicable)
  • Potential impact — what could an attacker achieve?
  • Suggested fix (optional but appreciated)
Do not open a public GitHub issue for security vulnerabilities. This protects users while the issue is being resolved. We aim to acknowledge reports within 48 hours.

2. Implemented Security Features

Active

AES-256-GCM Encryption at Rest

All files are encrypted on disk. The encryption key is separate from file content.

Active

Per-File Key Wrapping

Each file is encrypted with a unique ephemeral key. Only the wrapped key is stored, providing cryptographic isolation between files.

Active

Magic Byte + ZIP Manifest Validation

DOCX files are validated by ZIP magic bytes and internal word/document.xml structure. PDFs are validated by %PDF magic bytes.

Active

SHA-256 Integrity Hashing

Every file has an integrity hash computed on upload and verified on access.

Active

No IP Logging

Forwarding headers (X-Forwarded-For, CF-Connecting-IP, etc.) are stripped before reaching any route handler.

Active

Client-Side Dashboard

Upload history is stored in localStorage. No server-side association exists between a user account and their uploads.

Active

Pseudonymous Rate Limiting

Upload rate limits use an HMAC-derived tag, not a raw user ID. A database leak alone cannot link rate-limit records to an account.

Active

Ephemeral Storage

Files auto-delete between 1 minute and 24 hours. Expired files are purged from disk, not just marked inactive.

3. Known Limitations

We are transparent about current limitations so users can make informed decisions. Technical specifics that could assist exploitation are deliberately omitted.

IP Address Visibility

The application does not log or store IP addresses. However, the OS, web server, tunnel service, or hosting provider may retain connection-level logs outside the application's control. Application-layer IP stripping cannot prevent network infrastructure from recording IPs.

Planned: Official Cloudflare Workers deployment path where Cloudflare's IP anonymization hides visitor IPs at the edge before the request reaches application code.

Encryption Key Management

The master encryption key currently lives in .env alongside the application. For maximum security, the key and the data it protects should be stored separately — ideally with the key never touching the same disk as the encrypted files.

Planned: Document integration with external secrets managers (e.g., environment injection via CI/CD, AWS KMS, HashiCorp Vault, or Cloudflare Workers Secrets) so the key never co-locates with the data. Until then, self-hosters should inject ENCRYPTION_KEY via environment variables rather than committing it to disk alongside the database.

4. Supported Versions

Security updates are provided for the latest release only. Users running older versions are encouraged to upgrade. The project follows semantic versioning — check the releases page for the current version.

Dev Testing Build: This instance is a development/testing deployment. It may contain unreleased features or experimental changes. Do not use it for sensitive production data.

5. Best Practices for Users

  • Use the shortest expiry that meets your needs — files deleted sooner are safer.
  • If IP anonymity is required, access this service over Tor or a trusted VPN.
  • Do not share links to highly sensitive documents over untrusted channels.
  • Do not rely on this service as the only copy of important files.
  • Keep authentication tokens (access codes) secure and unique.

6. Self-Hosting Security Notes

  • Always set ENCRYPTION_KEY — without it, files are stored unencrypted on disk.
  • Inject ENCRYPTION_KEY via environment variables or a secrets manager rather than committing it to disk alongside the database.
  • Serve only over HTTPS — the tunnel provided by localtunnel is HTTPS by default.
  • Restrict access to the data/ directory — it contains the SQLite database and encrypted file blobs.
  • Keep Node.js and all dependencies updated.
  • Rotate the ENCRYPTION_KEY periodically (requires re-encrypting stored files).
