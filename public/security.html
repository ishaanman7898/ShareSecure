Security

Last updated October 4, 2026

Reporting a problem

If you find a security issue, email ishaanmanoor1@gmail.com instead of opening a public GitHub issue. Say what's affected, how to reproduce it, and what someone could do with it. We'll reply as soon as we can and let you know when it's fixed.

How files are protected

  • End-to-end encryption. On by default. Your browser encrypts the file, its name, notes and drawings with AES-256-GCM before uploading, using a key that only exists in the link after the #, which browsers never send to a server. Files are padded to standard sizes. Files sent to a username have the key sealed to that person, so only they can open it. Files shared by an assistant are sealed by the server, which then forgets the key.
  • Passcodes. Add one and the link is only half the key, so someone who only has the link can’t open the file.
  • Your password stays with you. Signing in proves you know your password without sending it (based on OPAQUE). Your private key is locked with a key only your browser gets from signing in.
  • Uploads and sends that can’t be tied to you. Your browser spends anonymous, blind-signed tokens instead of your sign-in, so the server limits how much each account shares without knowing which shares are whose.
  • Security codes. Every account has one (account menu → Security code). Compare them with people you send to; your browser also warns you if someone’s key ever changes.
  • A public key log. Every account’s key is recorded in an append-only log anyone can download and audit. Every key your browser is given has to come with proof it’s in the log, and your browser checks the log shows your own key. To read files meant for someone, a server would have to publish a second key for them where everyone can see it.
  • Links that work once. Turn on Works once and the file is erased the moment it’s opened. If anyone tries the link after that, you’re told: it was probably passed on.
  • File requests. A link you hand someone so they can send you a file. Their browser encrypts it to your key, which comes from the link itself, not the server, so the server can’t swap in a key of its own. It never sees the file, its name or what you asked for.
  • AI assistants ask before sending. An assistant can be tricked by something it reads into sending your files to a stranger, so a send to anyone not on your list waits for your OK. The list and the waiting sends are sealed to your own key. The assistant that runs on your computer (npx sharesecure-mcp) encrypts files there and keeps links out of the chat.
  • No third-party code. Every script is served from this site. The desktop app runs the site’s code from its own copy, so not even a compromised server can change it.
  • Check the site yourself. npm run verify-site compares every file this site serves with the published code, byte for byte. A public check runs it after every change and every day.
  • Encrypted storage. If you turn end-to-end encryption off, files are still encrypted on the server, each with its own key derived from a server master key.
  • Links that expire. You pick 1 hour to 10 days. After that the link stops working and the file is erased.
  • Not indexed. Pages tell search engines not to index or cache them, can't be embedded in other sites, and aren't cached by your browser.
  • No tracking. No analytics or third-party scripts, and ShareSecure's code doesn't log IP addresses.

What it doesn't protect against

  • The page you load. In a browser you trust the page the server sends each time. The public check catches a changed page for everyone, but not one sent only to you. The desktop app runs its own copy instead.
  • Who you send to. The server knows who a file was sent to and when, but not who sent it.
  • Whether a username exists. The key log names accounts by a hash of the username, so someone who guesses a username can check whether it has an account.
  • Anyone with the whole link. Without a passcode, a link is all it takes to open a file until it expires. Add a passcode, send to a username, and pick the shortest expiry that works.
  • Your network. Your internet provider and the hosting company can see that you connected. Use Tor or a VPN if you need to hide that.
  • The person you share with. They can screenshot or photograph a file even when downloads are turned off.

Good habits

  • Use the shortest expiry you can, or Works once.
  • Delete a share from Your shares as soon as it's been opened.
  • Send links through private messages, not public channels.
  • Compare security codes with the people you send to most.
